The main problem is duplicated ownership. Receipt edits, product identity, review policy, and background analysis each have more than one place that decides what happens next. Simplifying those boundaries will remove more complexity than reducing the number of tables or effects.

What I recommend

Start with plans 001, 002, 003, and 004. These address defects with clear causes and establish the draft, evidence, cache, and purchase models used by later work. Then make the backend own completion and retries before removing the UI workers.

Concrete defects behind the refactors

  1. Edits after approval can hide Save. Product selection and exclusion set dirty without clearing approved; the footer still selects navigation. Source trace; not reproduced on a device.
  2. Matching rules disagree about package evidence. A local probe found 50 cl versus 500 ml rejected by household matching but accepted by catalog matching. Another found that conflicting 10 BX and 15 BX evidence can pass the quantity path.
  3. A search summary can suppress details for 30 days. Both response types advance the same fetchedAt value. Missing nutrition or other detail fields can stay missing because the detail endpoint is skipped. Source trace; no live API request made.
  4. Price signals can use the wrong purchase basis. Local probes reproduced an excluded receipt receiving a warning and equivalent multipack purchases producing a 10× ratio when raw quantities were 10 and 1.

Reduce concepts, not just lines

  • One receipt draft with explicit operations.
  • One parser for package evidence, with separate policies for matching and consumption.
  • One review assessment and one transaction policy for receipt changes.
  • One explicit purchased-product identity.
  • One backend completion path, including skipped catalog work and retries.
  • One stable local store snapshot and one global query lifecycle bridge.

No replacement state library is needed. Convex, TanStack Query, and SQLite already serve useful, different roles.

Would another developer understand it quickly?

They could understand the product flow quickly. They would need much longer to explain who owns each state transition. A receipt may be created in processing, linked again in catalog work, changed through several edit paths, then repaired by a mounted UI component. The same purchase is interpreted separately by several reports.

Current flow

  1. 1 Capture/import saves local receipt images.
  2. 2 SQLite queue and session upload transport reserve and upload them.
  3. 3 Convex processing extracts, classifies, and creates household products.
  4. 4 Catalog matching may create another product identity and attach catalog evidence.
  5. 5 Product analysis resolves family, package, attributes, and purchased quantity.
  6. 6 Mounted receipt and session workers can restart unfinished enrichment.
  7. 7 Reports each select and interpret receipt lines.

Target flow

  1. 1 Capture owns input; the local queue owns durable upload.
  2. 2 Convex owns extraction and all server completion/retry paths.
  3. 3 Optional catalog work resolves a typed catalog or household identity.
  4. 4 Shared package evidence supports independent classification batches and quantity analysis.
  5. 5 One receipt-change policy applies review, revision, learning, and scheduling rules by change origin.
  6. 6 Screens subscribe; explicit user actions submit commands.
  7. 7 A common purchase projection feeds separate report reducers.

A six-stop walkthrough after the changes

  1. Capture and local storage: where images enter, how pending imports are acknowledged, and how unsent files survive restart.
  2. Backend pipeline: processing → optional catalog resolution → analysis, including failure and disabled-feature paths.
  3. Receipt state: extraction evidence, editable draft, review assessment, and committed receipt.
  4. Product vocabulary: exact catalog item, household product, family, reusable profile, and purchased quantity.
  5. Learning: explicit aliases, product mappings, and category-only memory with different trust rules.
  6. Reads and release controls: screen queries, complete report periods, offline caches, policy checks, and diagnostics.

A short architecture guide should name these owners and include the table glossary below. Do it after the structural work so the guide describes the actual code. Plan 013 includes it.

The missing responsibility: a structurally safe receipt

Receipt shape, receipt invariants, review readiness, and current write authority are four different responsibilities. A parsed receipt can still have missing optional fields, an unresolved amount, or an issue that requires review. It must not mean “approved”. Similarly, parsing cannot prove that the current user may change a stored receipt or that its revision is still current.

Current call shape, condensed

validateReceipt(data); // Returns void, or throws.
await correctProducts(ctx, householdId, editor, data, changes);
// Database writes AND changed data.lines are implicit outputs.

The caller relies on a successful check that changes no type, followed by an operation that changes both the database and its input object.

Proposed contract shape

type ReceiptParseOutcome =
  | { kind: "parsed"; receipt: ParsedReceipt }
  | { kind: "rejected"; issues: readonly [ReceiptInputIssue, ...ReceiptInputIssue[]] };

declare function parseReceipt(input: unknown): ReceiptParseOutcome;

declare function assessReceipt(input: {
  receipt: ParsedReceipt;
  duplicate: DuplicateAssessment;
}): ReceiptReviewAssessment;

declare function decideReceiptChange(
  input: ReceiptChangeInput
): ReceiptChangeDecision;

type ReceiptCommitAcknowledgement = {
  receiptId: Id<"receipts">;
  revision: number;
};

declare function commitReceiptChange(
  context: MutationCtx,
  input: ReceiptCommitInput
): Promise<ReceiptCommitAcknowledgement>;

Illustrative TypeScript signatures, not implemented APIs. ParsedReceipt is produced only by checked construction or invariant-preserving transformations. It must not be a broad type alias that callers can satisfy with unchecked data.

The parser retains the facts it checked. The assessment owns review readiness. The decision function computes the intended change from explicit evidence. The commit function owns database effects. Read current database facts, decide, and write inside the existing Convex mutation; this does not require another remote call or a generic command engine.
